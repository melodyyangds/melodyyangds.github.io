Finding the real causes of rework

Everyone had a theory about where our rework came from. For my Green Belt project, I tracked the cause of every reworked order so we could fix the right thing.

Method

The story

Problem
Rework was eating up a lot of the team's time. Past fixes went after the step people assumed was the problem, and nothing changed.
What I did
I ran a full DMAIC project. The key part was tagging every reworked order with a cause, so the Pareto came from real records instead of opinions. Control charts showed whether the process was stable before the change and whether the improvement stuck.
What changed
Most of the rework came from a few gaps in the process, not careless people. We closed them with digital forms, barcode scanning, a data logger, and fewer approval steps. It saved about $90K a year. (The cause names on this page are examples.)

Query behind the P-chart · BigQuery-style SQL, limits computed per phase 
WITH weekly AS (
  SELECT
    DATE_TRUNC(review_date, WEEK(MONDAY))                  AS week,
    IF(DATE_TRUNC(review_date, WEEK(MONDAY)) >= @change_week,
       'after', 'before')                                  AS phase,  -- by week, so no week splits
    COUNT(*)                                               AS orders_reviewed,
    COUNTIF(needs_rework)                                  AS rework_orders
  FROM work_order_review
  GROUP BY week, phase
),
phase_rate AS (
  SELECT phase, SUM(rework_orders) / SUM(orders_reviewed) AS p_bar
  FROM weekly
  GROUP BY phase
)
SELECT
  w.week, w.phase, w.orders_reviewed,
  SAFE_DIVIDE(w.rework_orders, w.orders_reviewed)         AS p,
  pr.p_bar                                                AS center_line,
  pr.p_bar + 3 * SQRT(pr.p_bar * (1 - pr.p_bar) / w.orders_reviewed)            AS ucl,
  GREATEST(0, pr.p_bar - 3 * SQRT(pr.p_bar * (1 - pr.p_bar) / w.orders_reviewed)) AS lcl
FROM weekly AS w
JOIN phase_rate AS pr USING (phase)
ORDER BY w.week;
